static auto stageFileReplacing (const QString &path, bool replace, const Filler &fill, QString *error=nullptr) -> bool
 The staged write every file QtPass puts into a store goes through: a temporary created next to path (an opaque name, exclusive, owner-only), filled by fill through its open handle, synced, then replaceFile()d under the name, and the object under the name afterwards checked to be the very file that was filled (opened without following, compared by device and inode). The name is never opened for writing, so a link a co-writer plants under it between the caller's check and the write is replaced as an entry rather than written through (QSaveFile resolves such a link at open); a file swapped under the temporary's name before the rename (a hard link to something of the user's, say) is caught by the comparison and reported, and what is under the name is left (removing it by name could take another writer's file that landed there since). Where the system cannot give both identities the write stands: on FAT and exFAT a rename moves the file ID, and those filesystems have no hard links to swap in either. On POSIX the temporary stays open until the comparison, so its inode number cannot be given to a file swapped in meanwhile (ext4 reuses the number of an unlinked, closed file at once).

Detailed Description

Static helpers that have no better home: setting up the process and the Git environment the way pass does, finding binaries and the default store, path and URL handling, and file operations that refuse to follow links.

Nothing here keeps state apart from the cached process environment, and nothing depends on a widget or a model. Store-boundary checks live in PathValidator, SSH agent discovery in SshAuthSock and template files in TemplateIO.

Set up the process the way pass sets up its own, before anything runs git or gpg or writes into the store.

Clears the variables that point git at another repository (GIT_DIR, GIT_WORK_TREE and the rest pass clears), and on Unix gives the processes QtPass starts (git, gpg, pass) the umask from PASSWORD_STORE_UMASK, 077 by default (Executor::setChildUmask()): what they create in the store is then the user's alone, as with pass. The variables that keep git in store's own repository, never one above it: GIT_CEILING_DIRECTORIES (gitCeiling()), and, when that ceiling holds git's list separator (":", ";" on Windows) and so cannot be one entry of the list, GIT_DIR and GIT_WORK_TREE naming the store's own .git and the store. ◆ isLaunchableWebUrl()

auto Util::isLaunchableWebUrl ( const QString & value) -> bool
static

Check whether a value is a safe, launchable web URL.

Stricter than protocolRegex(): intended to gate an "open in browser" action, where launching a non-web scheme would be a security risk. Returns true only when the trimmed value:

  • contains no control characters (CR, LF, NUL),
  • has an authority (host and port) of at most 259 characters, checked before QUrl normalises the host,
  • parses to a valid QUrl,
  • has scheme exactly "http" or "https" (case-insensitive),
  • has a non-empty host,
  • carries no embedded userinfo (user:password@host).

Deliberately rejects file://, javascript:, data:, ftp/ssh/webdav and scheme-less inputs (e.g. "www.example.com").

Parameters
valueCandidate URL string (typically a password-file field).
Returns
true if the value is a launchable http(s) URL, false otherwise.

auto Util::stageFileReplacing ( const QString & path,
bool replace,
const Filler & fill,
QString * error = nullptr ) -> bool
static

The staged write every file QtPass puts into a store goes through: a temporary created next to path (an opaque name, exclusive, owner-only), filled by fill through its open handle, synced, then replaceFile()d under the name, and the object under the name afterwards checked to be the very file that was filled (opened without following, compared by device and inode). The name is never opened for writing, so a link a co-writer plants under it between the caller's check and the write is replaced as an entry rather than written through (QSaveFile resolves such a link at open); a file swapped under the temporary's name before the rename (a hard link to something of the user's, say) is caught by the comparison and reported, and what is under the name is left (removing it by name could take another writer's file that landed there since). Where the system cannot give both identities the write stands: on FAT and exFAT a rename moves the file ID, and those filesystems have no hard links to swap in either. On POSIX the temporary stays open until the comparison, so its inode number cannot be given to a file swapped in meanwhile (ext4 reuses the number of an unlinked, closed file at once).
