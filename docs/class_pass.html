Detailed Description

Abstract base class for password store operations.

Pass provides an abstraction layer for password management, supporting both the native 'pass' utility and gopass/imitation backends. It handles:

  • Password file operations (show, insert, remove, move, copy)
  • GPG key management and Git integration
  • OTP generation
  • Random password generation

Subclasses must implement Git and password operations.

Paths: the operations take a path relative to the store, or an absolute path spelled from the store as configured (passStore), as the store tree and the dialogs build them. The link checks, pass names and Git paths are worked out against that spelling. A path spelled through the target of a store root that is itself a link is not under the store as named. Init() places such a folder from its canonical path; the other operations would check only the entry itself for a link and give pass and Git ../ names, so callers must not hand one over. Resolving every link instead is no way out: a removal would then reach a link's target, not the link.

◆ processErrorExit

void Pass::processErrorExit ( int exitCode,
const QString & err )
signal

An operation ended in failure: its process exited non-zero, could not be started or crashed, or the operation was refused.

The counterpart of the finished... signals for an operation that queued a command: it ends in one or the other. The main window releases the busy state and shows err in the password pane. One case emits both: when RealPass has removed a linked folder but could not commit that, this signal is followed by finishedRemove(), because the store did change.

Before anything is queued the paths differ, so a caller must not wait for this signal after every call. A path behind a link and an unfinished Git operation are refused with startingExecuteWrapper(), critical() and this signal. Other early checks, such as an entry that already exists, emit critical() alone and return.

insertFailed() and generateGPGKeysFailed() are emitted before this signal whenever their operation fails through a queued command, be it a non-zero exit, a crash or a process that could not be started, so their dialogs need not guess whose failure it is. generateGPGKeysFailed() also comes first when no gpg executable is configured and nothing is queued at all. A refusal that reaches this signal without queuing anything emits neither of them.

Parameters
exitCodeExit code of the process; -1 when it did not exit normally, 1 for a refusal.

A pull that stopped in a conflict leaves the repository part-way through an operation.
